# PRD：问古 · 古籍检索与阅读 Agent

> **这是一份回溯版 PRD（2026-11-14 补写）。** 项目从 D1–D7 冲刺长出来，先有代码和评测、后有定位，所以本文按**已实现的现状**反推需求，不假装当初有一份完整规格。
> 每一项需求都标注了状态与证据文件；没做的写「未做」，不写「即将支持」。

## 0. 为什么之前没有 PRD

三个原因，都是真的：

1. **驱动方式**：项目起点是一个技术问题（「古籍问答怎么才能不编造原文」），不是用户问题。第一版直接按「引用必须可追溯 + 指不到就拒答」写代码，需求散落在 README 和评测集里。
2. **七天冲刺**：D1–D7 的排期目标是「跑通 + 压测 + 公网可访问」，`docs/ROADMAP-v2.md` 承担了范围与验收的角色，但它回答的是「做什么功能」，不是「为谁解决什么问题」。
3. **定位改过**：早期是「命理古籍问答」，后来收敛为「古籍检索与阅读 + 历法换算」。定位一变，原来能写的用户故事就作废了，干脆没补。

代价也很直接：功能越加越多（三种 Agent 模式、排盘、记忆、MCP、授权确认），但「哪些是核心、哪些是演示、做到什么程度算完成」没有一份统一文档。这份 PRD 就是补这个缺口。

## 1. 问题定义

用户拿到一句古籍原文时，真正的问题是三个：

1. **这句话到底出自哪本书、哪一段？** 搜索引擎给的是网页，模型给的是转述，都不给可核对的原文位置。
2. **模型是不是编的？** 大模型会用现代常识补出一句「听起来像古籍」的话，用户无法分辨。
3. **我看不懂术语。** 「官星」「食神」「七杀」在原文里有特定语境，直接查词典会丢掉上下文。

现有替代方案的问题：通用问答模型不保证引用；古籍数据库能检索但不会解释；命理类产品把计算结果包装成「预测」，越过了文化展示的边界。

**本项目的回答**：把「检索到原文 → 标出出处 → 指不到就拒答」做成硬约束，接受「答得少」，换「答得可核对」。

## 2. 目标用户与场景

| 用户 | 场景 | 他们真正要的 | 本项目怎么满足 |
|---|---|---|---|
| 技术面试官 / 同行评审 | 看作品集、追问实现细节 | 能跑、能复现、敢写失败案例 | README + `docs/engineering.md` + 可重跑评测；局限清单 17 条 |
| 想自部署的人 | 在自己机器或服务器上跑一份 | 一条命令起服务、知道依赖和边界 | `scripts/serve.sh`、Dockerfile / compose、`.env.example` |
| 古籍 / 传统文化爱好者 | 查一句话的出处与上下文 | 原文位置、白话解释、不装神弄鬼 | 引用 chip 展开原文；拒答说明；盘面只做历法计算 |

**不是目标用户**：想要「算一卦 / 改运 / 付费化解」的人；需要医疗、法律、投资、婚姻、考试录取建议的人。这两类需求在本项目里是**明确拒绝**，不是「暂不支持」。

## 3. 产品目标与非目标

### 3.1 目标（v1）

1. 每条结论都能指回具体 `chunk_id`；引用编号非法或为 0 时判为不合规输出。
2. 检索片段答不了问题时拒答，并说明「这句古籍里没有直接依据」。
3. 支持多轮追问，但不把改写后的检索问句展示给用户。
4. 在 200 个 SSE 连接 / 20 条并发回答下稳定，超出容量返回 429 而不是排队崩溃。
5. 提供可复现的评测：检索、拒答、Agent、多轮四套，结果带代码版本与题目摘要。

### 3.2 非目标（v1 明确不做）

- 预测吉凶、改运、消灾、付费化解；
- 医疗、法律、投资、婚姻、考试录取建议；
- 用户账号体系、多租户、支付；
- 移动端原生 App、多地域容灾；
- 自建模型训练 / fine-tuning；
- 把排盘或牌面当作预测工具。

## 5. 成功指标（当前实测）

> 这是作品集项目，没有真实用户增长指标，所以只报**工程质量**与**可信度**两类可测数字。所有数字都对应仓库里的文件，可重跑。

| 类别 | 指标 | 当前值 | 说明 |
|---|---|---|---|
| 可信 | 编造引用 | 0/30 | 引用编号合法性 + 人工核验 |
| 可信 | 语料外拒答 | 10/10 | 30 题评测集中的 10 条 |
| 检索 | line R@5 / exact R@5 | 75.0% / 70.0% | 30 题、单人标注，属 development set |
| 检索 | 单路对照 | dense 62.5 / BM25 52.5（line） | 同口径 |
| 多轮 | 机械判定通过 | 19/20、18/20 | 失分是有证据仍拒答 |
| 性能 | 200 SSE + 20 并发回答 | 错误率 0.41%，TTFB P95 1.01s | CloudStudio 单机 8 核，2026-11-08 |
| 性能 | 检索接口 | 16 并发 130.5 QPS，P95 176.7ms | 不含 LLM |
| 工程 | 自动化测试 | 319 passed / 1 skipped | 本机装齐依赖；CI 另跑迁移冒烟与前端构建 |

**指标缺口（不回避）**：评测集只覆盖 16 部书（29 部无标点组没有题）；生成侧只校验引用编号，不校验「原文是否支持这句话」；30 条版是 development set，不能当泛化准确率。

## 7. 风险与依赖

| 风险 | 影响 | 当前处理 |
|---|---|---|
| 主题容易被读成「算命产品」 | 合规与信任 | 全站免责声明 + 明确不做清单 + 排盘只做历法计算 |
| 大模型编造原文 | 核心价值失效 | 硬约束引用编号 + 拒答 + 0/30 编造统计 |
| 评测集太小、单人标注 | 数字不可外推 | 局限清单明写 development set；不宣称泛化准确率 |
| 依赖第三方 LLM 配额 | 并发上限 | 全站额度闸门 + 429；不宣称超过供应商配额 |
| 单机部署 | 无高可用 | README 写明单机实测；多机未压测 |

## 8. 这份 PRD 怎么用

- 面试/评审时：先看 §1–§3 判断「解决什么问题」，再看 §4 的表格追问实现，最后用 §5 的数字对照 README 里的出处。
- 继续开发时：新需求先进 §4 表格并标优先级；改定位就改 §2/§3，别只改 README。
- 对外介绍时：不要引用「319 项测试」当产品质量证明——它证明的是工程纪律，不是回答准确率。
