## 00 一页摘要

问古是一个只回答「古籍原文里写了什么」的检索增强 Agent。它不预测、不建议，只做三件事：把问题检索到原文、把结论指回出处、指不到就拒答。

| 指标 | 数值 | 说明 |
|---|---|---|
| 已索引古籍 | **45 部** | 标点组 16 + 无标点组 29 |
| 检索 chunk | **8,681 块** | 约 340 万字 |
| line Recall@5 | **75.0%** | RRF 融合，20 道可答题 |
| 编造引用 | **0/30** | 编号全部落在 1..5 |
| 语料外拒答 | **10/10** | 没有一条被误判为可答 |
| 自动化测试 | **377 passed** | 另有 1 skipped（2026-11-18） |

> **边界先说。** 问古不是算命产品。八字、星盘、塔罗只做确定性的历法/天文计算与文化解释；解读不得改盘、不得断言吉凶，也不提供医疗、法律、投资、婚姻、考试建议。

核心承诺只有一句：答案里的每个编号，都能展开成一段真实存在的原文。为了守住这句话，系统宁可拒答，也不让模型用自己的常识补写古籍。这份文档记录的就是这条承诺如何落到检索、生成、校验、并发与部署上。

## 01 问题与定位

用户拿到一句古籍原文时，真正的问题不是「这句话什么意思」这么简单，而是三个可验证的问题：

**01 / 出处 — 这句话出自哪本书、哪一卷、哪一段？**
搜索引擎给网页，模型给转述，都不给可核对的原文位置。

**02 / 真伪 — 模型是不是编的？**
大模型会用现代常识补出一句「听起来像古籍」的话，普通用户无法分辨。

**03 / 语境 — 这个术语在原文里怎么用？**
「官星」「食神」「七杀」有特定语境，查词典会丢掉上下文，换一本书也可能不同。

| 替代方案 | 能给什么 | 缺什么 |
|---|---|---|
| 通用问答模型 | 流畅解释、现代类比 | 引用不保证，原文可能编造 |
| 古籍全文数据库 | 原文与检索 | 不会解释术语，也不处理口语化提问 |
| 命理类产品 | 排盘、运势、结论 | 把计算包装成预测，越过文化展示的边界 |
| **问古** | 检索原文 + 编号引用 + 拒答 + 确定性排盘 | 覆盖窄、答得少，只回答语料内的问题 |

> **定位。** 一个可核对的古籍阅读助手：先证明原文在哪，再解释它说什么。

项目起点是一个技术问题——「古籍问答怎么才能不编造原文」——不是一份完整的用户研究。七天冲刺里，`docs/ROADMAP-v2.md` 承担了范围与验收，README 承担了结果与局限。这份 PRD 是事后补的：保留简版 `docs/PRD.md` 的 R1–R18 编号，补齐行为规格、非功能要求、数据与评测口径，以及一份可查的证据索引。

## 02 用户与场景

| 用户 | 场景 | 他们真正要的 | 本项目怎么满足 |
|---|---|---|---|
| 技术面试官 / 同行评审 | 看作品集、追问实现细节 | 能跑、能复现、敢写失败案例 | README + `docs/engineering.md` + 可重跑评测；17 条局限清单 |
| 想自部署的人 | 在自己机器或服务器上跑一份 | 一条命令起服务、知道依赖和边界 | `scripts/serve.sh`、Dockerfile / compose、`.env.example` |
| 古籍 / 传统文化爱好者 | 查一句话的出处与上下文 | 原文位置、白话解释、不装神弄鬼 | 引用 chip 展开原文；拒答说明；盘面只做历法计算 |

> **不是目标用户。** 想要「算一卦 / 改运 / 付费化解」的人；需要医疗、法律、投资、婚姻、考试录取建议的人。这两类需求在本项目里是**明确拒绝**，不是「暂不支持」。

### 三条主要路径

**A · 查一句出处**
输入口语化问题 → 检索 Top-5 原文 → 带 `[n]` 编号回答 → 点引用 chip 展开《书名·卷·篇》 → 不满意可切换 Agent 模式重查。

**B · 追问与换书**
第二轮问「那它和阳刃是一回事吗？」→ 先改写成独立问题 → 只带最近 3 轮 / 1,200 字 → 本轮引用隔离 → 有证据就答，没有就拒答。

**C · 排盘，再问术语**
输入出生信息 → intake 缺字段则追问 → 确定性排盘 → 解读时按盘面检索古籍片段、只讲不算 → 问「桃花煞是什么」回到 RAG，仍然要求引用原文。

### v1 明确不做

- 预测吉凶、改运、消灾、付费化解
- 医疗、法律、投资、婚姻、考试录取建议
- 用户账号体系、多租户、支付
- 移动端原生 App、多地域容灾
- 自建模型训练 / fine-tuning
- 把排盘或牌面当作预测工具
- 上千 QPS 的回答吞吐（受上游 LLM 配额约束）
- 为了「像 RAG 产品」而引入不必要的基础设施

> **成功的定义。** 不是「什么都能答」，而是「答了的都能核对，没答的说明为什么」。这也是所有取舍的最后一把尺。

## 04 产品结构与人流

访客只看到两页：问古籍、排盘。记忆是辅助面板，维护能力收进 `?admin=1`。这个分层是有意的：公开页不暴露检索后端、RRF、BM25 这些工程词，避免把「可核对」讲成「技术炫技」。

| 入口 | 界面 | 内容 |
|---|---|---|
| 01 / ASK | 问古籍 | 单轮 RAG / 单 Agent / 多 Agent；流式回答、引用展开、会话管理 |
| 02 / CHART | 排盘 | 八字、星盘、塔罗；结构化 intake；解读只讲不算 |
| 03 / MEMORY | 记忆 | 跨会话偏好；可查看、可删除；两步确认；不作为引用证据 |
| 04 / ADMIN | 维护页 | 检索后端、Top-k、逐轮轨迹、数据中台、评测中台 |

### 一次回答的链路

```
提问 → 改写（仅多轮 / standalone） → 混合检索（dense + BM25 → RRF）
     → Top-5 证据（chunk_id + 书名卷篇） → 生成（can_answer + answer + citations）
     → 引用校验（1..5 → chunk_id） → 输出（回答 / 固定拒答）
```

### 三种模式，同一套引用纪律

| 模式 | 谁决定检索 | 工具预算 | 调用 / 题 | 30 题通过 | 适合 |
|---|---|---|---|---|---|
| 单轮 RAG | 固定链路 | 1 次检索 | 1.0 | — | 单跳释义、快速问答 |
| 单 Agent | 模型自己选工具 | 6 步 | 3.0 | 23/30 | 多跳、换工具、先排盘再检索 |
| 多 Agent | Supervisor 分工 | 6 步 | 7.6 | 26/30 | 跨书对比、缺口回补 |

### 流式事件契约

| 事件 | 何时发 | 关键字段 | 前端怎么处理 |
|---|---|---|---|
| `step` | 一次工具调用完成 | agent、tool、args、ok、chunk_ids | 展开步骤与证据 |
| `stage` | 多 Agent 阶段变化 | agent、detail | 显示 planner / retriever / verifier / synthesizer |
| `delta` | 正文增量 | text | 追加预览 |
| `done` | 回答完成 | 完整 ChatResponse | **用 done.answer 覆盖正文** |
| `error` | 链路失败 | message、request_id | 显示错误与 request id |

> **读流式的两个前提。** `delta` 只是预览：终稿可能被拒答归一化改写，收到 `done` 后必须用 `done.answer` 覆盖，不要拼接后直接当最终答案。
>
> 心跳默认 15s；客户端断开即取消上游任务。200 个「保持中的连接」走 `GET /v1/events`，只发心跳，不占回答槽。

### A · 可信问答

#### R1 · 引用必须能指回原文（P0 · ✅）

- 每次只把 RRF Top-5 拼进上下文，每段前缀 `[n]《书名·卷·篇》`；空字段不拼。
- 回答若声称 `can_answer=true`，必须至少带一个 1..5 的引用编号；编号映射到本轮工具实际返回的 `chunk_id`。
- 编号越界、引用不存在，或「声称能答却零有效引用」，一律判 `invalid_output`，不进入正常回答。
- 前端把 `[n]` 渲染成 chip，点击通过 `POST /chunks` 取原文与书名。

**验收**：30 条任务 0 条编造引用；0 条 invalid_output；19 条可答回答中 15 条至少一条引用命中 gold（78.9%）。

**证据**：`src/rag.py`、`src/agent.py` 的 `_finalize`、`tests/test_agent_guardrails.py`、README §3.2

#### R2 · 指不到就拒答（P0 · ✅）

- 检索片段不足以回答时输出 `can_answer=false`，正文统一成固定拒答文案，引用为空。
- 拒答原因写入 `refusal_reason` 供 trace 与评测使用，不把模型的长篇解释当成拒答理由展示。
- 拒答是一等输出，不是异常兜底；前端用正常回答样式显示，并给出「换个问法 / 换本书」的建议。

**验收**：10 条语料外问题 10/10 拒答；可答题误拒 1/20（q01），作为已知缺口记录，不当作达标。

**证据**：`eval/refusal_results.csv`、README §3.2、§4.1

#### R29 · 引文白话解读（P1 · 🟡）

- 引用 chip 展开后可在「原文 / 白话释义」之间切换；默认原文，点白话才请求。
- 译文**不是证据**：不进引用链、不参与 `can_answer` 判断，卡片固定标注「译文仅辅助阅读，不算引用依据」。
- 接口 `POST /v1/chunks/interpret`，一次最多 4 段；按完整原文 sha1（含提示词版本与截断上限）缓存到 `data/interpret_cache.jsonl`；全命中缓存时不调模型、不占回答槽、不扣额度。
- 提示词只允许逐句对译：不增不减、保留专名、不判吉凶、不做现代类比；空串表示无法成句翻译。超过 1500 字的原文只译开头一段，用 `truncated` 标注。
- 单条翻译失败只标在那一项上，其他引用照常可读。

**验收**：`tests/test_interpret.py` 覆盖缓存命中 / force / 截断 / 空译文 / 超长译文 / 单条失败 / 全命中不进模型；2026-11-18 真实模型单条走通，第二次请求 `cached=true`。

**缺口**：没有对照译文，忠实度未评测；超长原文分段译未做（局限 #21、R18 的阅读侧对应项）。

**证据**：`src/interpret.py`、`src/api.py`、`frontend/src/components/Sources.tsx`、`frontend/src/interpretCache.ts`、README §6.2.3

#### R3 · 混合检索，不把权重写死（P0 · 🟡）

- dense：BGE-M3 1024 维，numpy 精确余弦；BM25：字二元组 + 倒排索引；两路各取 40 条候选，RRF `k=10` 融合，取 Top-5。
- `mode` 可覆盖单路，便于对照；jieba 与 reranker 是开关，默认关闭。
- 不引 pgvector / HNSW：8,681 × 1024 约 34 MB，精确扫描毫秒级，少一次网络往返，也不改评测口径。

**验收**：line R@5 75.0%（dense 62.5 / BM25 52.5）；exact 70.0%；`/retrieve` 16 并发 130.5 QPS、P95 176.7ms。

**缺口**：评测题只覆盖 16 部标点书；参数在同一批题上搜出又报告，有过拟合风险；20 题下 1 题就是 5 个百分点。

**证据**：`src/retrieval.py`、`src/bm25_fast.py`、`eval/baselines.md`、`loadtest/retrieve.py`

#### R19 · 流式输出与断线恢复（P0 · ✅）

- SSE 事件：`step`（一次工具调用完成）、`stage`（多 Agent 阶段）、`delta`（正文预览）、`done`（完整响应）、`error`。
- `delta` 只是预览；`done.answer` 是最终稿，前端收到后覆盖正文，不拼接。
- 空闲 15s 发 `: keep-alive`；客户端断开即取消上游任务；刷新后通过 `runs` 回放。
- 200 个「保持中的连接」走 `GET /v1/events`，只发心跳，不占回答槽；回答流走 `/chat/stream` 或会话流。

**验收**：浏览器真实提问逐 token；200 连接 10 分钟 7,800 次心跳、0 错误；`done` 覆盖逻辑有测试。

**证据**：`src/sse.py`、`src/answer_stream.py`、`tests/test_agent_stream.py`、`tests/test_answer_stream.py`

### B · 多轮与会话

#### R4 · 多轮只用于消解指代（P0 · 🟡）

- 只取最近 3 轮 / 1,200 字，从旧到新丢；追问先改写成独立问题，历史只用于指代与省略补全。
- 每轮引用只来自本轮工具返回的 chunk；上一轮的旧结论不能当本轮证据。
- 改写超时、额度不足或 JSON 非法时退回原问题，单轮链路不受影响。
- 改写后的检索问句不展示给用户，避免让用户学习系统内部措辞。

**验收**：v9（2026-11-18，代码 `21f3d9b`）20 条多轮对话 **20/20**（单 Agent）、**20/20**（多 Agent），两者都计入重跑；首轮分别为 19/20、18/20。追问改写命中 49/49；引用隔离违规 0。拒答反向对照 10/10、误拒 1/20。

**缺口**：多 Agent 的 `mt08`（正官格 → 用神怎么定）首轮改写丢了「正官」，后两次通过，属改写抖动（约 2/3），不算稳定通过；多 Agent 首轮 18/20 比单 Agent 的 19/20 低一条，调用数约翻倍，仍无优势。下一步是给改写加「上一轮对象词必须出现」的校验。

**证据**：`src/conversation.py`、`eval/multiturn.jsonl`、`eval/run_multiturn.py`、README §3.5

#### R6 · 会话可新建、切换、删除、刷新恢复（P1 · ✅）

- 服务端存会话、消息、运行记录；匿名 id 存浏览器 localStorage，不要求登录。
- 刷新后恢复历史消息、引用与待确认卡片；删除会话级联删除消息与运行记录。
- 流式回答结束后持久化本轮；失败时不写半条消息。

**验收**：刷新不丢历史与待确认卡片；删除后列表与详情一致；换身份需刷新页面（SPA 只改 hash 不会重载）。

**证据**：`src/api_conversations.py`、`frontend/src/pages/ChatPage.tsx`、`tests/test_conversations_api.py`

#### R27 · 会话摘要，最小闭环（P2 · ✅）

- 新消息累计 ≥8 条时，把较早内容压成摘要，保留最近 4 条原文。
- 摘要随会话注入，但不作为引用证据；引用仍只来自本轮检索。
- 摘要失败不影响主链路；没有单独的质量评测。

**验收**：摘要生成 / 注入有单测；长会话不因历史超长而报错。

**证据**：`src/conversation.py`、`tests/test_conversation.py`

### C · 回答模式

#### R5 · 三种回答模式，同一套引用纪律（P1 · ✅）

- `rag`：固定一次检索 + 一次生成；`agent`：单 Agent 自己选工具；`multi`：Supervisor / Retriever / Verifier / Synthesizer 分工。
- 三种模式共用 6 步工具预算、同一套引用白名单、同一条拒答出口；原生 function calling 默认，JSON ReAct 通过 `MINGLI_TOOL_MODE=json` 回滚。
- 公开页默认 RAG；Agent 模式展开每一步工具、参数、chunk_id 与耗时。

| 指标 | 单 Agent | 多 Agent | 读法 |
|---|---|---|---|
| 30 题通过 | 23/30 | **26/30** | development set，不是盲测 |
| 双书显式检索 | 10/22 | **20/22** | 多 Agent 的主要优势 |
| LLM 调用 / 题 | 3.0 | 7.6 | 成本翻倍 |
| P50 / P95 | 38.0s / 54.9s | 60.2s / 78.6s | P95 就是最慢一两题 |

**缺口**：30 条版每系统只跑 1 次，题型与 prompt 在同一轮迭代里互相改过；26/30 不能外推成「换一批题也有 87%」。

**证据**：`src/tool_loop.py`、`src/agent_multi.py`、`eval/results_agent_d2_single30_fix.json`、`eval/results_agent_d2_multi30_fix.json`

### D · 排盘

#### R9 · 算和讲分开（P1 · 🟡）

- 排盘只由历法 / 天文库计算：八字用 `lunar_python`（节气定月、立春换年）；星盘用 `pyephem` 地心视黄经 + 整宫制；塔罗 78 张，seed 可复现。
- 解读由 LLM 组织语言，prompt 明确「盘面是既定事实，不得重算、不得补充盘里没有的星体或神煞」。
- 解读会按盘面关键词（日主 / 十神 / 五行、上升 / 行星、牌名）加用户问题检索 Top-5 古籍片段，作为术语与结构的说明材料进 prompt；模型用 `[n]` 引用片段，接口返回 `citation_map`（`marker → chunk_id`），越界编号丢弃。
- 检索只是增强：语料或 embedding 不可用时退化为纯盘面解读并照常返回；盘面本身是证据，解读没有引用不算不合规，不因此改判拒答。
- `/v1/fortune/read` 用请求参数在服务端重算盘面，忽略客户端传来的 chart；塔罗 seed 缺省时服务端生成。
- 不做吉凶、生死、疾病、灾祸、婚姻成败断言；医疗 / 法律 / 投资问题明确超出范围。

**验收**：19 条计算测试 + 4 条解读检索测试：立春换年、五行 = 8、性别只影响大运顺逆、太阳落狮子座、同输入同输出、同 seed 同牌、12 宫覆盖 12 星座；片段进入 prompt、引用映射与越界丢弃、检索失败退化、解析失败仍保留片段编号。

**缺口**：解读文本质量没有评测集（R18）；星盘未做真太阳时校正；塔罗正逆位 50/50，不宣称预测含义；解读检索只取 Top-5，未评测片段与盘面的相关性。

**证据**：`src/fortune/bazi.py`、`astro.py`、`tarot.py`、`interpret.py`、`tests/test_fortune*.py`、`tests/test_fortune_interpret.py`、README §11

#### R20 · 排盘前先问清楚（P1 · ✅）

- `POST /v1/fortune/intake` 返回 `ready` 或 `need_input`；缺字段时返回结构化问卷（label / type / range / example / ask），而不是让模型猜。
- 只有可选字段允许默认值，并在 `defaults` / `warnings` 中明示；不静默使用「北京时间 / 默认地点」。
- 前端把问卷渲染成表单，用户补全后再排盘。

**验收**：缺出生时间 / 地点时返回 `need_input`；默认值被列出；有单测。

**证据**：`src/fortune/intake.py`、`src/api_fortune.py`、`tests/test_fortune_api.py`

### E · 记忆

#### R7 · 长期记忆可查看、可删除、不越权（P1 · ✅）

- 记忆跨会话保存，按 `(user_id, kind, key)` 唯一；关键词触发抽取，每次最多 3 条。
- 敏感信息正则过滤后丢弃；记忆只用于偏好与背景，不作为引用证据。
- 访客可查看、删除自己的记忆；访问他人记忆返回 404；前端两步确认删除。

**验收**：记忆隔离、删除、过滤均有测试；记忆不进入他人会话。

**缺口**：关键词启发式，不做向量记忆 / 自动遗忘；匿名 id 不是鉴权，隔离边界是「同一浏览器」。

**证据**：`src/memory.py`、`src/api_conversations.py`、`tests/test_memory.py`、README §6.4

### F · 工具与互操作

#### R8 · 有副作用的工具必须一次性授权（P1 · ✅）

- 外部 / 副作用工具默认标记 `SIDE_EFFECT`，调用前必须确认；待确认动作持久化，前端显示卡片。
- 批准后返回一次性 token；用户带 approvals 重发请求；token 以 sha256 存储，绑定工具名 + 参数，600s 过期，原子消费，校验失败即拒绝。
- 不做永久 allow；无状态 `/chat` 不支持副作用工具；多 Agent 不暴露副作用工具。

**验收**：一次性消费、过期、参数不匹配、重复使用、缓存失效均有测试。

**为什么**：工具结果可能被注入；授权是产品边界，不是模型自觉。

**证据**：`src/tool_policy.py`、`src/api_conversations.py`、`tests/test_approvals.py`、`tests/test_cache_invalidation.py`

#### R10–R12 · MCP：既能被调用，也能调用别人（P1 · ✅）

- server 暴露 7 个工具：`search_classics`、`fetch_chunk`、`list_books`、`search_terms`、`draw_bazi`、`draw_astro`、`draw_tarot`；支持 stdio 与 streamable-http；stdio 不污染 stdout。
- client 从配置挂载外部 server，工具名加 `mcp__<server>__<tool>` 前缀，合并进 function calling；策略 `allow` / `read_only` / `deny`。
- 单个 server 失败不影响本地工具；没配置就不起子进程、不发网络请求。
- HTTP transport 设置 `MINGLI_MCP_TOKEN` 后要求 Bearer；缺失 / 错误 401；共享密钥不是 OAuth，改 token 需重启。

**验收**：server 工具 schema、stdio 干净、client 发现 + 调用、auth 401 均有测试；`scripts/check_mcp_client.py` 起真实子进程验证。

**缺口**：外部工具没有「按会话是否进 prompt」的开关（R17），目前只有全局白名单。

**证据**：`src/mcp_server.py`、`src/mcp_client.py`、`src/tool_policy.py`、`tests/test_mcp_*.py`

### G · 容量、成本与部署

#### R13 · 20 个回答槽与 200 个连接分开算（P0 · ✅）

- 同步 `/chat` 与流式 `/chat/stream` 共用 Redis 全局 20 槽；多 worker 共享，不会变成 4 × 20。
- 槽满立即 429 + `Retry-After`，不排队；在线 SSE 不排队是产品决策，排队会把首 token P95 推高。
- 200 个保持连接走 `GET /v1/events`，只发 hello + 心跳，不占回答槽。
- 没配 Redis 时退化为进程内闸门，`/health` 显示 `local`；Redis 故障同样退化并计数，不静默。

**验收**：同一 10 分钟窗口：连接 200/200、0 错误、7,800 次心跳；回答 480/482 成功、错误率 0.41%、TTFB P95 1.01s、完成 P95 4.30s；21 并发出现 429。

**缺口**：单机 8 核；Postgres 写竞争与跨机扩容没有压过；20 并发里的 2 条 429 来自闸门瞬时竞争，仍在 1% 验收线内。

**证据**：`src/gate.py`、`loadtest/README.md`、README §6.1.1

#### R14 · 一条命令起同源形态（P1 · ✅）

- `scripts/serve.sh up` 起 Redis → API（127.0.0.1:8000）→ Nginx，并打印四条验收；`status` / `down` 管状态。
- Dockerfile + compose 提供 Redis / Postgres / embed；`requirements.txt` + `alembic upgrade head` 建 9 张表；embedding 随仓库提供，开箱可检索。
- 重建索引：`python src/build_index.py` 校验语料，`python src/embed.py` 重新编码。

**验收**：四条验收（直连 401、经 Nginx trace 404、`/health` 200、`/` 200）；README 数字有复现命令。

**证据**：`scripts/serve.sh`、`deploy/README.md`、Dockerfile / compose、`.github/workflows/ci.yml`

#### R21 · 语义缓存只服务单轮 RAG（P2 · ✅）

- 精确层：问题 NFKC + 小写 + 压空白 + 去尾标点后哈希，key 含 mode / top_k，Redis `SETEX` 24h，多 worker 共享。
- 语义层：问题向量余弦 ≥ 0.95，进程内有界 LRU（1,000 条），只和同 mode / top_k 比；Redis 普通镜像无 RediSearch，不做全局向量索引。
- 只缓存单轮 RAG；agent / multi、带 history、访客自带 key、`can_answer=null`、`invalid_output` 都不缓存。
- 命中直接返回 `done`（流式先补整段 delta），usage 全 0、`cached=true`、`cache_kind` 标 exact / semantic；命中不占额度；`X-No-Cache: 1` 绕过。

**验收**：精确 / 语义命中、排除条件、缓存失效、额度不扣均有测试；压测用 `NO_CACHE=1` 避免数字做假。

**缺口**：语义命中各进程各自学习；真实缓存命中率未统计。

**证据**：`src/semcache.py`、`tests/test_semcache.py`、`tests/test_cache_invalidation.py`、README §6.1.2

#### R23 · 访客自带 Key 与全站额度（P1 · ✅）

- 服务端配了 key 就用服务端 key；否则访客可通过 `X-DeepSeek-Key` 自带，key 只存在当前会话，不写日志、不落盘、不进 trace。
- 服务端 key 的额度：每会话 6 次、全站每天 300 次；计数在 `data/.quota.json`，保留 7 天，重启不清零。
- 访客自带 key 不计数；全站刷满 300 后当天只能自带 key。DeepSeek 预付费，余额为 0 自动停。

**验收**：额度闸门、缓存命中不扣额度、自带 key 不计数的测试；公开页在没有服务端 key 时提供填写入口。

**缺口**：单会话限制挡不住脚本，全站日额度是唯一硬闸门；没有按 IP 限流。

**证据**：`src/guards.py`、README §6、`data/.quota.json`（gitignore）

#### R28 · 公网部署与密钥隔离（P1 · ✅）

- Nginx 同源托管前端与 `/api`，服务端用 `envsubst` 注入 Bearer token；浏览器不持有上游 API key。
- API 绑 `127.0.0.1`，只允许 Nginx 访问；`/metrics` 对外 404，`/trace` 需 token。
- CloudStudio 单机部署，工作区停止链接即失效；固定入口需域名 + Cloudflare Tunnel 或年付 VPS（`deploy/VPS.md`）。

**验收**：2026-11-08 公网四条验收通过；浏览器真实提问逐 token；日志 `grep -c DEEPSEEK_API_KEY api.log = 0`。

**缺口**：共享 token 不是用户级鉴权；单机无高可用；CloudStudio 不是 7×24 托管。

**证据**：`deploy/README.md`、`deploy/VPS.md`、`scripts/serve.sh`、README §6

这些数字都有明确的测试条件，不是产品 SLA。单机、单次、开发集上的结果，换机器或换题库都要重跑。

| 维度 | 口径与现状 | 边界 / 缺口 |
|---|---|---|
| **性能** | 200 + 20 同窗：TTFB P95 1.01s、完成 P95 4.30s；检索 16 并发 130.5 QPS / P95 176.7ms；Agent P50 38.0s / 60.2s。 | 单机 8 核；P95 样本只有 20–30 条；不作 SLA 承诺。 |
| **容量** | 20 个全局回答槽；200 个空闲 SSE 连接；超容量 429 + `Retry-After`，不排队。 | 上游 LLM 配额是硬上限；加槽位不等于加容量。 |
| **可靠性** | Redis 故障退化到进程内并计数；LLM 多 key failover / 熔断只在首个 delta 前切换；SSE 断开即取消。 | 没有多机高可用；Postgres 写竞争未压测。 |
| **安全** | API Bearer；Nginx 服务端注入 token；API 绑 loopback；访客 key 仅会话；MCP token；授权 fail-closed。 | 共享 token 不是用户级鉴权；没有账号 / 权限模型。 |
| **隐私** | 匿名 id；记忆可查看 / 删除；敏感信息正则过滤；日志不含 key。 | 匿名 id 不是鉴权；隔离边界是同一浏览器；正则可能漏检。 |
| **成本** | 逐题 token 统计；单价用环境变量传入；额度闸门 6 / 会话、300 / 日。 | `runs.cost_usd` 仍写 0；金额要靠对账单回填。 |
| **可维护性** | 377 passed / 1 skipped；39 个测试文件；CI 跑全量测试、迁移冒烟、前端构建。 | 测试覆盖工程契约，不覆盖回答忠实度。 |
| **兼容性** | Python 3.12；Node 20；Docker；Linux 部署；Windows 开发走 WSL。 | BGE-M3 权重需下载；纯 CPU 编码要数小时。 |
| **可访问性** | 390 宽实跑；移动端抽屉；本页与产品共用高对比纸墨色；键盘 focus 可见。 | 未做系统性的 WCAG / 键盘路径审计。 |

## 07 数据与评测

评测的目标不是把分数做大，而是让「不编造」这件事可以被检查。所有结果都保留逐题明细与代码版本；语料或参数一变，旧数字就作废。

### 语料与索引

| 项 | 规模 | 说明 |
|---|---|---|
| 已采集清洗文本 | 152 部 | 原始语料层，不等于已索引；字数未单独统计 |
| 已索引 | 45 部 / 8,681 块 / 约 340 万字 | 标点组 16 部 2,830 块 + 无标点组 29 部 5,851 块 |
| 未切分 | 107 部 | 未进入索引，也未出题 |
| chunk 规格 | 目标 450 字 / 上限 700 / 重叠 60 | 句级重叠；定义跨块时仍可能切断答案 |
| 向量 | 8,681 × 1024 / 约 34 MB | BGE-M3，归一化；随仓库提供 |
| 术语 | 324 条 | 用于 jieba 对照；默认仍是字二元组 |

### 四套评测

| 套件 | 规模 | 指标 | 结果 | 口径 / 缺口 |
|---|---|---|---|---|
| 检索 | 30 题（20 可答 + 10 语料外） | Recall@5 / MRR，exact + line | line 75.0%；exact 70.0% | 只覆盖前 16 部书；单人标注 |
| 拒答 | 10 条语料外 | 拒答率 | 10/10 | 可答题误拒 1/20，单独记录 |
| Agent | 30 个任务 | 通过数 / 调用数 / 延迟 | 23/30；26/30 | development set；每系统只跑 1 次 |
| 多轮 | 20 条对话（4 类 × 5） | 机械判定通过 | 20/20；20/20（v9，含重跑） | 首轮 19/20、18/20；mt08 改写抖动按 2/3 记 |

### 检索策略对比 · line Recall@5

20 道可答题，k=10 / cand=40：

| 策略 | line R@5 | exact R@5 |
|---|---|---|
| dense | 62.5 | 52.5 |
| BM25 | 52.5 | 42.5 |
| **RRF 融合（默认）** | **75.0** | **70.0** |

两个口径一起报，避免只挑好看的那个。

### 分题型：为什么要做 Agent

| 题型 | n | dense | BM25 | RRF |
|---|---|---|---|---|
| 单跳释义 | 8 | 88% | 38% | 75% |
| 口语改写 | 4 | 25% | 50% | 50% |
| 应用推理 | 4 | 50% | 75% | **100%** |
| 跨书对比 | 3 | 67% | 83% | 83% |
| 多跳综合 | 1 | 50% | 0% | 50% |

这张表是「把检索改成 Agent」的直接依据：单跳题 dense 碾压 BM25（88% vs 38%），应用推理题反过来（50% vs 75%）。一个全局融合权重只能取平均；要让两类题都不掉分，只能让模型按题目类型自己选检索方式。

> **不能这样说。**
>
> - 不能说「准确率 87%」：26/30 是 development set 上的单次结果，题库与 prompt 在同一轮迭代里互相改过。
> - 不能说「359 项测试证明回答可靠」：测试覆盖工程契约，不覆盖「原文是否支持这句话」。
> - 不能说「P95 4.3 秒是 SLA」：20–30 条样本的 P95 就是最慢的一两题。
> - 不能说「语义缓存命中率 xx%」：真实命中率没有统计。
> - 不能说「解读质量已评测」：只有 19 条计算测试，文本质量仍在 R18。

每份评测结果都带 `code_commit` 与 `tasks_sha256`；跑批第一行打印 `[provenance]`。这不是仪式：上一轮曾因为工作区停在旧提交，白跑了一整批 75 分钟。

## 09 风险与开放问题

| 风险 | 影响 | 当前处理 |
|---|---|---|
| **主题被读成「算命产品」** | 合规与信任 | 全站免责声明 + 明确不做清单 + 排盘只做历法计算 |
| **大模型编造原文** | 核心价值失效 | 引用编号硬约束 + 拒答 + 0/30 编造统计 |
| **评测集太小、单人标注** | 数字不可外推 | 明写 development set；不宣称泛化准确率 |
| **依赖第三方 LLM 配额** | 并发上限 | 全站额度闸门 + 429；不宣称超过供应商配额 |
| **单机部署 / CloudStudio 过期** | 无高可用、链接失效 | README 写明单机实测；固定入口方案在 `deploy/VPS.md` |
| **语义缓存误命中** | 答非所问且看似有据 | 只缓存单轮 RAG；阈值 0.95；排除低置信输出；命中率待统计 |
| **记忆隔离边界** | 同一浏览器外的越权风险 | 匿名 id + 404 + 删除；不宣称账号级安全 |
| **Agent 成本与延迟** | 多 Agent 调用 7.6 次 / 题 | 默认 RAG；Agent 作为可选模式，公开页可切换 |
| **文档与代码漂移** | 数字过期、结论失真 | 结果带 provenance；本文标注日期与基线；重跑命令可查 |

### 开放问题

1. 定位如何避免被读成算命？是靠文案、命名，还是靠产品上彻底不出现「运势」二字？
2. 评测扩到 80 条并双人标注后，75.0% 的 line R@5 还能保持吗？
3. 语义缓存阈值 0.95 在长尾问题上会不会误命中？需要怎样的监控与回滚？
4. 匿名 id 不是鉴权，记忆隔离的信任边界应该怎么对外表述？
5. CloudStudio 过期后，固定入口用域名 + Tunnel，还是直接买年付 VPS？
6. 出口的「有证据不得拒答」判据，会不会把原本正确的保守拒答改坏？
7. 解读质量用什么 rubric 才能既不神化、也不把「像不像」当唯一标准？
